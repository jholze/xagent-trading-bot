# Evidence #822: coalesce dca_guard skip events (N = 2 per lot) and dedupe DCA reflector lessons

Base commit: `a1508cc` (origin/staging). Measured with the in-memory store and an
in-memory RAG retriever (hash embeddings, no Weaviate), same scenario on both sides:
30 older market events for one synthetic symbol, one `volume_breakout` event at
minute 5:30, then 40 `dca_guard` skips (one every 90 s for one hour) for tenant
`henry`, with the writer's RAG indexing on. After every skip the DCA reflector
(`min_events=5`) and the cycle RAG indexer (`index_store_into_rag`) run, as in the
memory cycle. The "alternating" rows alternate the reason set between
`[dca_guard_below_avg]` and `[dca_guard_below_avg, dca_guard_max_rounds]`.

| metric | before | after |
|--------|--------|-------|
| DCA skip rows among the last 40 events for the symbol (fact window) | 39 | 2 |
| same, alternating reason sets on the same lot | 39 | 2 |
| skip count stored on the `latest` row | none | 40 |
| `first_ts` / `last_ts` / `reason_counts` stored | no | yes |
| `volume_breakout` from the same hour in the 40-event window | yes (last slot) | yes |
| live "skipped add-ons often" lessons in `memory_lessons` | 1 | 1 |
| "skipped add-ons often" RAG chunks (5, 6, 7, ... clones) | 36 | 1 |
| RAG chunks for DCA skip rows (writer `dca_decision` + indexer `event`) | 80 | 2 (one per row) |
| sniper input `dca_lesson_count` / `dca_lesson_negative_count` for the symbol | 1 / 1 | 1 / 1 |
| sniper input `rag_negative_count` (top 3 for "SYM trade dca loss") | 3 | 3 |
| sniper `mem_score` RAG term `-min(1.5, 0.4 * rag_negative_count)` | -1.2 | -1.2 |
| guard decision for a lot below average (`evaluate_dca_guard`) | blocked, `dca_guard_below_avg` | blocked, `dca_guard_below_avg` |

## What changed

- `strategies/dca_decision_event.py`: skip decisions (`result.skip=True`) belong to
  one family per lot, keyed `tenant|symbol` (positions carry no lot id). The family
  has at most `SKIP_EVENTS_PER_LOT = 2` rows (code default, N = 2 decided by Kay):
  `first` and `latest`. `latest` holds `count` (family total), `first_ts`,
  `last_ts`, the newest `reason_codes` / `applied` and a `reason_counts` map.
  Non-skip decisions keep one row each with the old per-timestamp id. A store error
  is logged and writes nothing; it never falls back to one row per skip.
- `intelligence/memory/store.py`: new `MemoryStore.record_coalesced_skip`. No
  read-modify-write of the count: `latest` is incremented with one
  `find_one_and_update` (`$inc` count and reason counts, `$set` last_ts / newest
  fields), `first` is created with `insert_one` (duplicate key means it exists),
  `latest` is created with `insert_one` from `first` and falls back to `$inc` on a
  duplicate key. Any raised store error propagates and nothing is rewritten. The
  in-memory store runs the same method over a small dict collection with one lock
  per call (single-document atomic, like Mongo).
- Family reset: when the newest row of the family is older than
  `memory.coin_facts.lookback_hours` (existing setting; code default 72 h, committed
  `config.json` has 336 h), the next skip replaces `first` (count 1, new `first_ts`)
  and deletes `latest`.
- RAG: the writer no longer indexes coalesced skip rows. The cycle indexer owns
  them with `chunk_key = event id`, so each row has exactly one live chunk that is
  replaced when the count changes. `chunk_id_for` honours `chunk_key`; the DCA
  reflector and the indexer use the lesson id as `chunk_key` for DCA lessons.
- `intelligence/memory/dca_reflector.py`: a family's `latest` row stands for the
  whole family (`count`, `reason_counts`); its `first` row then counts zero.
  So the per-symbol lesson and the `harvest_skip` / `deploy_boost` rules still see
  the real number of skips and reasons.

No change to the guard, the policy result, sizing, order flow, `strategies/dca.py`,
`config.json`, tenant config, `*.live.json`, `risk/`, `execution/` or `aria_bot.py`.

## Effect on the DCA sniper memory score

`strategies/dca_context.py` (unchanged) feeds `services/dca_sniper/checklist.py`
`mem_score` with `dca_lesson_count` / `dca_lesson_negative_count` (from
`memory_lessons`, already one row per lesson id before this PR, so unchanged) and
`rag_negative_count` (polarity of the top 3 RAG hits). In the scenario above the
top 3 stay negative (1 lesson + 2 skip rows), so the RAG term is unchanged at
-1.2. The sniper sees fewer duplicate negatives: before, 36 lesson clones and
80 skip chunks could fill the top 3 on their own. When a symbol has other RAG
material (trades, positive lessons, news), those now reach the top 3 more often,
so `rag_negative_count` can go down and `mem_score` up compared to the flood.
That is the intended effect of removing duplicates, but it is a change in a
sniper input.

## Known limits / transition

- Lot identity is `tenant|symbol`. A later lot on the same symbol joins the same
  family unless the family is older than the lookback (then it restarts).
- Rows and RAG chunks written before this change (one row per skip, 5/6/7/...
  lesson clones) are not deleted. They leave the 40-event fact window as newer
  events arrive or when they fall outside the fact lookback
  (`rule_switches.pre_trade_gate.facts.lookback_hours`, 336 h committed). Until
  then the window and RAG still show the old flood. The transition lasts until
  40 newer events have arrived for the symbol (the review estimated about 72 h);
  on quiet symbols it can last up to the lookback. Not measured on paper yet.
- After a family reset, the RAG chunk of the deleted `latest` row stays until a
  new `latest` row for that lot is indexed (same chunk key, then replaced).
