# Evidence #711: stamp strategy_tier at the buy, and make the 20M stable mcap floor reachable

Paper only (staging). Release framework rule 5: evidenced and tested bug fix, no backtest and no new trial.

## Problem (measured on the Railway export of 2026-10-31, read-only)

| Measure | default | henry |
|---|---|---|
| open lots | 145 | 110 |
| open lots with `strategy_tier = null` | 48 | 42 |
| ... from `gainer_relvol` | 27 | 19 |
| ... with no source | 14 | 17 |
| ... from `sensor` | 7 | 6 |
| lots whose `entry_snapshot.strategy_tier` is set | 0 | 0 |

Every snapshot has `strategy_tier = None`, so no buy path passes a tier into `update_position`.
The tier was only set lazily by `lock_strategy_tier` the first time a decision cycle analysed the open lot.
That never happened for many relvol and sensor lots from early September on.

There was a second bug in `risk_manager` (long mcap floor). A new BUY has no lot yet, so `_tier_key(None)` fell back to `volatile`.
As a result every new entry got the 5M floor, and the configured 20M floor for stable coins never applied to a new entry.

## Before / after

| Case | before | after |
|---|---|---|
| New lot from a DE cycle (analysis has `volatility_tier`) | `strategy_tier` null until a later cycle | stamped at the first fill, `strategy_tier_source = "entry"` |
| New lot from gainer relvol (no DE analysis) | null | live classify on the buy timeframe (never raises); unknown stays null |
| New lot, no hint, coin class large_cap / micro / meme | null | `stable` / `volatile` from the coin class |
| Lazy lock on a legacy lot | sets the tier silently | sets the tier and marks `strategy_tier_source = "first_cycle"` |
| DCA add on a lot with a tier | unchanged | unchanged (no overwrite, test) |
| Long mcap floor, stable entry at mcap 6M | 5,000,000 (volatile fallback) -> allowed | 20,000,000 -> blocked |
| Long mcap floor, volatile entry at mcap 6M | 5,000,000 -> allowed | 5,000,000 -> allowed |
| Long mcap floor, unknown tier at mcap 4.9M | 5,000,000 -> blocked | 5,000,000 -> blocked, logged "strategy_tier unresolved, legacy volatile floor" |
| `entry_snapshot` cost provenance | fee only | + `cost_tier`, `coin_class`, `slippage_pct` |
| Issue #711 red tests (`tests/unit/test_tier_at_entry_rr.py`) on origin/staging 1d2a041f | 4 failed, 1 passed | 5 passed |

The switch `volatile_altcoin.freeze_tier_on_entry` (default True) decides whether the entry tier is stamped.
With False, the old lazy behaviour is kept.

## Changed tests (and why)

- `tests/unit/test_entry_snapshot_600.py::test_passed_strategy_tier_is_not_read_from_the_lot` now expects the passed tier (`volatile`) on the lot. The old test pinned `None`, which was the bug.
- `tests/unit/test_entry_sensor_15m.py`: the mcap mock changed from 10M to 25M. The fixture coin (ATR 3 %) classifies `stable`, so the 20M floor now applies as configured. The test is about the 15m sensor, not about the floor.

## Risk and rollback

- Behaviour change: new stable entries with a market cap between 5M and 20M are now blocked, as configured. The export has no mcap per entry, so the count of affected entries is not quantified. This is an assumption, not a measurement.
- Rollback: set `volatile_altcoin.freeze_tier_on_entry = false` for the stamp (needs a tenant config change, so Jens' OK), or revert this PR. The mcap fix is code-only; revert the PR to undo it.
- Known residuals, not changed here:
  - `execution/recovery.py:863` rebuilds orders without a tier.
  - `risk_manager` ~2283 (`elig_mcap` for open lots) is untouched.
